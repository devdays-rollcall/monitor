# Работа с монитором маршрутов

Монитор принимает события участников туристической группы и показывает их маршруты на карте. Android-приложение, сбор координат и p2p-передача между телефонами находятся вне этого репозитория. Здесь находятся HTTP API, worker, база, очередь и веб-интерфейс.

## С чего начать

- `openapi.yaml` — контракт HTTP API, описания полей и пример запроса. Сначала изменяйте контракт, затем реализацию и проверки.
- `README.md` — команды запуска, тестирования и развёртывания.
- `backend/` — Java 25 LTS, Quarkus и Gradle. API и worker используют один код, но запускаются отдельно через `APP_ROLE`.
- `frontend/` — React, TypeScript, Base UI, styled-components и MapLibre GL. Фронтенд собирается в статику и работает с backend только по HTTP.
- `backend/migrations/` — SQL-миграции PostgreSQL. Они применяются вручную, не при старте приложения.
- `compose.yaml`, `infra/` и `Makefile` — локальный запуск; `compose.production.yaml` — конфигурация приложения для сервера.
- `scripts/demo.py` — создание небольшой демонстрационной группы; `tests/` и `frontend/tests/` — проверки API и браузерных сценариев.

## Как устроен приём событий

API проверяет запрос и публикует всю пачку одним сообщением в NATS JetStream. Ответ `202 Accepted` возвращается после подтверждения публикации и не означает запись в PostgreSQL. API не должен ждать worker или базу при приёме событий.

Worker независимо читает очередь и сохраняет пачку одной транзакцией. Группа и участники создаются при обработке первого сообщения, поэтому сразу после `202` чтение может вернуть `404` или ещё не содержать новые события. После успешной записи worker подтверждает сообщение. При временной ошибке он повторяет обработку; некорректное сообщение завершает без повторов. Доставка — at least once.

Stream `GROUP_EVENTS`, subject `group.events.batch`, consumer `events-writer`; хранение файловое, политика `WorkQueue`. Обработанные сообщения удаляются после подтверждения, необработанные — через 24 часа. Не удаляйте stream или его данные ради перезапуска: там могут быть непрочитанные события. Максимальный размер NATS payload — 2 МиБ.

Уникальность события — `(group_id, id)`. Повтор с тем же ID не создаёт запись и не перезаписывает исходную; различающееся содержимое фиксируется в журнале. Сохраняйте эти свойства при изменениях API, очереди и worker.

## Как пользоваться API

Полное описание полей, ограничений и ответов находится в `openapi.yaml`. Актуальный адрес сервиса: `https://rollcall.vareonix.cc`; локальный адрес по умолчанию — `http://localhost:8080`.

Группа не регистрируется отдельным запросом. Лидер создаёт ключ из 32 криптографически случайных байтов в base64url без padding и передаёт его участникам. Каждое устройство хранит свой UUIDv4 участника. Каждое событие получает UUIDv4 один раз; при p2p-передаче и повторной отправке сохраняйте его ID и содержимое.

Ключ группы передаётся в `Authorization: Bearer <group_token>` и даёт право читать и отправлять события, а также создавать ключи просмотра. `sender_id` — отправитель HTTP-пачки; `member_id` — автор конкретного события. Они могут отличаться. Пустой `events` — heartbeat. Пачка ограничена 500 событиями и телом размером 1 МиБ.

`GET /api/v1/events` возвращает события страницами в порядке записи в базу. Передавайте `next_cursor` как `cursor`, пока ответ не вернёт `null`; не разбирайте формат курсора. Для маршрута сортируйте точки каждого участника по `recorded_at`.

`POST /api/v1/share-links` с ключом группы создаёт независимый случайный ключ просмотра с префиксом `view_`. Он позволяет только читать события. Сервер хранит хеши ключей. У ключа просмотра нет срока действия или механизма отзыва. Ссылка хранит его в query-параметре `view`, а состояние карты — в `member`, `lat`, `lon` и `zoom`. Старые ссылки с `#view=` также открываются. Не помещайте ключ группы в URL.

Ключ просмотра в query может попасть в журналы сервера и историю браузера. Яндекс Метрика в `frontend/index.html` включена по запросу владельца с Вебвизором и `location.href`, поэтому адрес с ключом просмотра может попасть и в аналитику. Не утверждайте, что этот ключ скрыт от внешних сервисов. Не публикуйте реальные ключи и секреты в репозитории или логах.

## Интерфейс

Показывайте маршруты участников разными стабильными цветами. Не соединяйте точки разных участников и оставляйте разрыв, если между соседними измерениями прошло более 30 минут. Выделяйте последнюю точку; направление показывайте на метке, когда оно передано. Выбор участника, положение и масштаб должны сохраняться в ссылке.

Карточка точки показывает все переданные поля, включая дополнительные поля `data`; отсутствующие измерения не заменяются нулями. Учтите нулевые значения, длинные строки, клавиатуру, мобильные экраны, загрузку и ошибки. Перед завершением UI-изменений проверяйте основные и крайние состояния.

Дизайн компактный и минималистичный, с единым лёгким стеклянным эффектом. Используйте Base UI и styled-components; не добавляйте лишние элементы или бизнес-логику. В интерфейсе называйте пользовательский токен «ключом».

Карта использует векторный стиль Maptoolkit Hiking с данными OpenStreetMap. Его бесплатные условия ограничивают использование для навигации и решений, связанных с безопасностью; указание авторства требуется условиями поставщика, но было скрыто по просьбе владельца. Учитывайте это при изменении и публикации карты.

## Локальный запуск

Нужны Docker Compose, Make, Node.js 24 и pnpm. Из корня проекта:

```bash
make up
```

При первом запуске новой базы дождитесь PostgreSQL и примените миграции в другом терминале:

```bash
docker compose exec -T postgres psql -U user -d monitordb -v ON_ERROR_STOP=1 < backend/migrations/001_init.sql
docker compose exec -T postgres psql -U user -d monitordb -v ON_ERROR_STOP=1 < backend/migrations/002_share_tokens.sql
```

Повторно не применяйте миграции к существующей базе. Локальная база называется `monitordb`, пользователь — `user`, пароль — `password`. Данные PostgreSQL и NATS находятся в Docker volumes. Не удаляйте их без явного запроса.

Для демонстрационной группы выполните `python3 scripts/demo.py` и используйте выведенный ключ. `MONITOR_URL` меняет адрес API для скрипта и тестов. На сервере также есть тестовый маршрут; его дополнительные показания моделируются и не являются реальными измерениями.

## Изменения и проверки

Делайте минимальное изменение, необходимое для задачи. Не добавляйте незапрошенные сценарии, сервисы, бизнес-правила и абстракции. Разделяйте логически разные части кода пустыми строками и не пишите комментарии в коде. Не редактируйте сгенерированные Java DTO и `frontend/src/generated/` вручную.

Java форматируется через Spotless и Google Java Format в режиме AOSP, как в проекте `/Users/dan/itmo/java/java-reflection`:

```bash
backend/gradlew -p backend spotlessApply
backend/gradlew -p backend test
```

Во frontend используйте pnpm. Сборка генерирует клиент из OpenAPI:

```bash
cd frontend
pnpm install --frozen-lockfile
pnpm build
pnpm test:e2e
```

Для тестов нужен запущенный стек; браузер Playwright устанавливается командой `pnpm exec playwright install chromium`. `CHROME_BIN` позволяет указать существующий Chrome. API-проверки запускаются из корня:

```bash
python3 -m unittest discover -s tests -v
```

Тесты создают данные в указанной базе. Тесты с `MONITOR_FAULT_TESTS=1` останавливают и запускают контейнеры; используйте их только в изолированном локальном стеке. Если указан другой `MONITOR_URL`, убедитесь, что `COMPOSE_PROJECT_NAME` указывает на тот же стек для проверок, обращающихся к Docker.

SQL пишите в lowercase и используйте параметризованные запросы. Для каждого нового или изменённого SQL-запроса проверяйте план через `EXPLAIN`; при подходящих данных используйте `EXPLAIN (ANALYZE, BUFFERS)`. Изменяющие запросы с `ANALYZE` запускайте только в изолированной базе. Если план проверить не удалось, сообщите об этом.

При Java-задачах применяйте установленные подходящие навыки: `java-coding-standards`, `122-java-type-design`, `124-java-secure-coding`, `125-java-concurrency`, `401-frameworks-quarkus-core`, `402-frameworks-quarkus-rest`, `411-frameworks-quarkus-jdbc`, `java-junit`, `421-frameworks-quarkus-testing-unit-tests` и `422-frameworks-quarkus-testing-integration-tests`. Для интерфейса выбирайте подходящие `frontend-design`, `ui-ux-pro-max`, `web-design-guidelines`, `design-system` и `design`. Для коммитов используйте `git-commit`.

## Продакшен и Git

Продакшен использует существующие PostgreSQL, NATS и общий ingress Nginx сервера. Приложение запускается отдельным Compose-проектом, а frontend отдаётся существующим Nginx как статика. Образы backend собираются локально для архитектуры сервера и публикуются в GHCR; на сервере сборку не выполняйте. Подробности и пути — в `README.md`.

Развёртывайте изменения на сервер только по явному запросу. Перед обновлением проверяйте совместимость миграций и сохраняйте возможность отката. Не меняйте и не перезапускайте чужие сервисы, общий ingress, базу или очередь без необходимости. Проверяйте фактическое состояние сервера, а не полагайтесь только на документацию.

Сохраняйте существующие незакоммиченные изменения. Не добавляйте `AGENTS.md` в коммит и не отправляйте его в репозиторий без отдельного разрешения владельца.
